## Установка

1. Сохранить/export важные методички. Применять сначала в тестовой среде.
2. Применить `supabase/resource-library-delete.sql` в Supabase SQL Editor **после** `files.sql`, `file-inventory.sql`, `cloud-sync.sql`, `resource-library.sql`. Скрипт не удаляет файлы при установке. Если повторно применять `cloud-sync.sql`, повторно применить и этот SQL последним (он заменяет restrictive DELETE policy).
3. `npm run build`.
4. `node --experimental-strip-types --test tests/resource-groups.test.mjs tests/resource-delete-sql.test.mjs`.
5. `node --experimental-strip-types --test tests/*.test.mjs`.
6. `npm run dev`, проверить сценарии ниже в двух профилях браузера.

## Поведение

- `workingAssets` — постоянные локальные изображения по `[scope,sha]`. Старые встроенные изображения видны и могут быть явно сохранены в библиотеку; массовая миграция — этап 6.
- Приватный Storage не становится публичным. Предпросмотр — авторизованная загрузка с SHA-проверкой, URL Blob освобождаются. Приватный файл не попадает в локальную библиотеку при простом просмотре.
- В облаке одна логическая карточка для известного SHA, внутри которой отдельные приватный и публичные экземпляры. Файлы старого каталога с неизвестным SHA не объединяются наугад. Публичные файлы не переносятся/не удаляются автоматически. Ручное удаление исторических публичных изображений намеренно заблокировано до этапа 6: старые офлайн-документы на других устройствах могут содержать ссылки.
- Выбор в редакторе работает из локального каталога офлайн; из облака — при наличии аккаунта и интернета. Передаём старому редактору обычный data URL через `originalImage`.
- Обычная загрузка файла в облачной вкладке оставлена для PDF/PPTX/JSON; новый загрузчик изображений работает с приватным Storage. Импорт изображения из устройства в облако оставляет его локальную копию; это намеренное поведение. Имя приватного файла в облачном каталоге пока генерируется по SHA; локальное имя сохраняется, публичные папки/переименование остаются. Метаданные приватных папок — не часть этого патча.
- Локальное удаление проверяет сырые документы, состояние синхронизации, резервные и исходные JSON в одной транзакции IndexedDB. Это консервативная проверка: исторический оригинал может заблокировать удаление даже без активных связей. Удаление приватной облачной копии никак не удаляет локальные копии.
- SQL-резервирование облачного удаления защищает от записи ссылки в момент удаления. Storage API авторизуется одноразовым token в существующем storage lease. Удаление через SQL из storage.objects запрещено. Непроверенные сведения блокируют удаление в интерфейсе; сервер отдельно проверяет рабочие ссылки и резервирование. Существующие облачные документы, включая тела корзины, защищены до очистки истории. Новые документы должны встраивать приватные изображения вместо URL; старые клиенты нужно обновить.
- Если сетевой ответ удаления потерян, reservation остаётся. Не снимать её автоматически и не удалять storage.objects вручную. Оператор должен проверить завершение запроса, фактическое наличие/отсутствие объекта через Storage API и отсутствие ссылок. Только после проверки можно снять именно данную reservation в SQL Editor (по owner_id, sha и token), не трогая бинарный объект. Утерянный ответ не является подтверждением удаления.

## Обязательные ручные и интеграционные проверки (не выполнены генератором)

- Импорт PNG/JPEG/WebP/SVG, один SHA в нескольких методичках и шаблонах; одна запись в IndexedDB и одна карточка на известный SHA в облаке.
- Скачивание на устройство B, перезапуск без интернета, вставка изображения из библиотеки, фон слайда, экспорт JSON, изменение размера/перетаскивание и статус сохранения.
- Удаление методички из облака не удаляет изображение. Повторное добавление не удваивает объект. Корзина и резервные копии блокируют удаление.
- Удаление используемого изображения отклоняется даже при прямом вызове RPC / Storage API; другая учётная запись и anon не могут читать/удалять чужое.
- Два клиента одновременно сохраняют документ и пытаются удалить его ресурс; одна операция должна быть отклонена, не должно появиться документа с отсутствующим объектом. Проверить именно реальный Supabase Storage, включая потерю ответа, token header, RLS и повторную загрузку после удаления.
- Проверить старые публичные ссылки, публикации, PDF/PPTX/JSON, папки и переименование. Не считать отсутствие локальных ссылок доказательством отсутствия ссылок на других отключённых устройствах; массовую миграцию и проверку legacy выполняем на этапе 6.
- Сравнить галерею на узком и широком экране. Проверить scroll, диалог предпросмотра, picker, ошибки доступа и неизвестное использование.

До прохождения этих тестов не развёртывать на рабочем сайте. PGlite тест проверяет SQL/RLS на имитации Storage, а не реальные бинарные операции и сетевые гонки.
