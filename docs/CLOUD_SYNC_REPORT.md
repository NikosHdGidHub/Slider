# Slider Cloud Sync & Library

[Ветка разработки dev-2026-11-27_04-55-22](https://github.com/NikosHdGidHub/Slider/tree/dev-2026-11-27_04-55-22)

Базовая ревизия `main` — `ed4e857`. Изменения подготовлены для отдельной ветки разработки. Публикации и развёртывание рабочего сайта остаются самостоятельными операциями. SQL проверен в локальном PostgreSQL через PGlite.

## Реализация

- **Рабочие документы.** Методички и пользовательские шаблоны сохраняются на устройстве и автоматически отправляются в закрытую библиотеку. IndexedDB записывает документ и запись очереди вместе. Базовая ревизия, идентификатор операции и хэш защищают от перезаписи изменений и повторной отправки после потери ответа.
- **Ресурсы и автономность.** Облачная копия содержит ссылки по SHA-256 на встроенные изображения и шрифты. Сервер подтверждает ревизию после загрузки ресурсов. Скачанные рабочие копии восстанавливаются в полный редактируемый формат, очередь и конфликты переживают перезагрузку. Импорт и экспорт используют прежний переносимый JSON.
- **Конфликты.** Несовместимые правки приостанавливают синхронизацию одного UUID. Владелец может просмотреть версии, выбрать одну или сохранить обе. Копия получает новый UUID. Доступна временная локальная резервная копия. Удаление идёт через сохраняемую отметку с 30-дневным сроком восстановления. Активная сессия предупреждает о параллельном редактировании.
- **Курсы.** Общая панель синхронизации включает очередь методичек и шаблонов, курсы, ресурсы и ошибки. Организационные команды курсов и конфликтная модель сохранены.
- **Публикации.** Отдельный индекс содержит название, дату, счётчик слайдов и возможную миниатюру текущей публикации. Галерея и компактный список поддерживают курсы, фильтр, глобальный поиск, ручной порядок и прежние URL. Публикация обновляется явным действием.
- **Передача.** Мобильный список использует каталог метаданных, поиск и фильтр по курсу. Кнопка передачи остаётся у нижней границы. Проверку авторизации, подтверждение кода, срок действия и валидацию фактически опубликованного UUID выполняет существующий протокол.

## Миграция и развёртывание

1. На отдельном тестовом проекте проверьте резервное копирование БД и Storage. Экспортируйте важные старые локальные черновики перед обновлением рабочих устройств. Для установки требуется действующая конфигурация `setup.sql`, `templates.sql`, `files.sql`, `file-inventory.sql`, `courses.sql` и `qr-transfer.sql`.
2. Выполните [cloud-sync.sql](../supabase/cloud-sync.sql) в SQL Editor тестового проекта и сверите перенесённые UUID и ревизии шаблонов. Скрипт использует существующий допуск `atlas_course_access`, сохраняет исходные записи для проверки, закрывает запись в старую таблицу и не меняет файлы публикаций.
3. Опубликуйте тестовую сборку со своим URL проекта, публичным ключом и UID. В двух профилях выполните вход, создание и независимые изменения. Проверьте восстановление сети, чистый гостевой профиль, приватный Storage и старые публичные ссылки. Затем заполните индекс из «Опубликованных» и проверьте QR-передачу.
4. Для рабочего проекта согласуйте окно обновления, резервную копию и замену старых клиентов. Проверьте квоты и согласуйте расписание очистки просроченных записей. [Подробный порядок развёртывания и отката](SUPABASE_SETUP.md#облачная-синхронизация-рабочего-пространства)

## Ограничения

- Облачный каталог получает компактные метаданные всего доступного набора. Карточки и мобильные строки выводятся порциями. У публикаций без подходящего изображения используется стандартная пиктограмма. У черновиков, ещё не загруженных на устройство, карточка показывает метаданные и пиктограмму.
- Существующие публикации получают полноценные названия после первого индексирования владельцем. При обрыве между Storage и индексом карточка сохраняет UUID и может быть переиндексирована. Статический пользовательский HTTPS-адрес остаётся внешней зависимостью. Команда офлайн-подготовки сохраняет доступное изображение.
- Приватные объекты Storage защищены от физического удаления клиентом. Просроченное тело удалённого документа и старые квитанции очищаются операторским заданием. Автоматическая физическая сборка бинарных ресурсов отсутствует. Резервные копии конфликтов хранятся в профиле браузера, где разрешён конфликт, и доступны для экспорта.
- Живой тестовый Supabase, публичный CDN, реальные телефоны и установленные на них PWA требуют отдельной проверки с доступом владельца. Клиентская сборка всё ещё получает предупреждение Vite о размере основного чанка.

В повторном прогоне проверены устранённые дефекты. Переход в «Опубликованные» теперь обновляет каталог после изменений на другом устройстве. Импортированная локальная запись участвует в первом согласовании, даже когда браузер уже хранит облачные метаданные того же UUID. Экран QR больше не запрашивает каталог второй раз в скрытой библиотеке.

Команды проверок:

```sh
npm ci
npm run build
node --experimental-strip-types --test tests/*.test.mjs
VITE_SUPABASE_URL=https://atlas-test.supabase.co VITE_SUPABASE_ANON_KEY=sb_publishable_fixture \
  VITE_ADMIN_UUID=00000000-0000-4000-8000-000000000001 \
  npm run build -- --outDir /tmp/atlas-cloud-fixture
python tests/typography_browser.py
python tests/library_browser.py --cloud-dist /tmp/atlas-cloud-fixture
python tests/courses_browser.py --cloud-dist /tmp/atlas-cloud-fixture --zoom
ATLAS_LIBRARY_CAPTURES=/tmp/atlas-captures python tests/cloud_sync_browser.py /tmp/atlas-cloud-fixture --zoom
```

Для браузерных сценариев требуются Python Playwright и Chromium. Тестовые переменные используются для маршрутов, перехватываемых локальным стендом.

## Производительность

Измерения сделаны в Chromium с локальным HTTP-сервером и имитацией Supabase. Для каждого объёма использовались одинаковые по структуре демонстрационные методички. Байты относятся к UTF-8 содержимому JSON, без HTTP-заголовков и сжатия. Столбец прежнего подхода показывает суммарный объём полных JSON на той же выборке. Прежний интерфейс запрашивал каждый JSON отдельно вдобавок к списку Storage.

| Публикации | Прежние полные JSON, Б | Новый каталог, Б | Открытие раздела, мс | Поиск, мс | QR, мс | Обновление рабочих метаданных, мс |
| ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| 10 | 39 661 | 1 682 | 87 | 39 | 244 | 184 |
| 100 | 396 692 | 16 893 | 121 | 19 | 288 | 301 |
| 500 | 1 983 892 | 84 893 | 150 | 32 | 368 | 340 |
| 1000 | 3 967 893 | 169 894 | 153 | 34 | 364 | 347 |

На каждом объёме QR-подборщик делал один запрос каталога и скачивал ноль полных JSON. Комбинированное действие теста «открыть рабочую библиотеку → синхронизировать → открыть “Опубликованные”» делало три запроса метаданных публикаций с учётом обновления на каждом переходе и ноль запросов тел документов. При открытии одной карточки публикации был загружен только её JSON. Поиск проверен по последней записи за пределами первой видимой порции.

На выборке из 1000 записей QR-экран с искусственной задержкой ответа каталога 150 мс загружался за 463 мс. `navigator.storage.estimate()` после сценария показал 5 947 686 Б для профиля, из них 1 392 640 Б в IndexedDB и 4 524 339 Б в Cache Storage. Значения зависят от браузера и состава профиля.

У тестовой методички с повторяющимся PNG и пользовательским шрифтом переносимый исходник занимал 193 689 Б, компактный JSON — 11 078 Б. Два уникальных бинарных объекта заняли 135 172 Б. При повторе после потерянного ответа и после изменения текста дополнительных загрузок ресурсов не было.
