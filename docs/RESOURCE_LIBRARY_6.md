# Этап 6. Миграция и итоговый аудит ресурсов

## Перед установкой
- Применены этапы 4–5 и SQL `resource-library-delete.sql`; сохраните исходники и экспортируйте ценные методички/шаблоны, включая уникальные локальные копии. Резервная копия патча — только исходники, не IndexedDB и не Supabase.
- Проверьте сначала на тестовом экземпляре Supabase и тестовом браузерном профиле. Закройте редакторы во всех вкладках и на остальных компьютерах. Не очищайте IndexedDB.
- Патч не запускает SQL и не выполняет миграцию данных сам. Примените `supabase/resource-library-audit.sql` после `cloud-sync.sql`, `resource-library.sql` и `resource-library-delete.sql`; после повторной установки базовых SQL повторите SQL этапов 4–6 по порядку.

## Миграция (Мои файлы → Обслуживание и проверка библиотеки)
1. «Проверить устройство»: прочитать документы, включая резервные копии, проверить SHA ресурсов. Сохранить отчёт.
2. «Мигрировать локальные документы»: упаковать старые документы и семидневные резервные копии по SHA. Внешние изображения скачиваются; если недоступны, исходная запись не меняется. При наличии сети можно восстановить повреждённый/отсутствующий ресурс из собственного приватного Storage только при совпадении SHA. Транзакция сверяет сырой снимок записи и отклоняет незавершённые синхронизации. Старые неизменённые документы не переписываются. При входе в аккаунт ресурсы локального пространства копируются в пространство владельца без удаления исходных ресурсов. Новая ревизия создаётся только при изменении/ремонте записи. Существующие облачные копии синхронизируются обычным способом; новых облачных копий эта миграция не создаёт.
3. Дождаться окончания обычной синхронизации. Ошибки и конфликты решить штатными средствами, затем повторить миграцию.
4. «Мигрировать документы только в облаке»: отдельное явное действие. Читаются и проверяются ресурсы непосредственно из Storage. Прежние облачные UUID и владельцы сохраняются, применяется CAS по серверной ревизии, ресурсы загружаются перед JSON, `create_doc=false`. Локальная копия не создаётся. Документы с локальными копиями/незавершёнными операциями пропускаются, корзина не меняется. Другие устройства с устаревшей ревизией должны пройти обычное разрешение конфликтов. При потере ответа повторный запуск проверяет текущую версию.
5. «Индексировать старые публичные изображения»: скачать фактические байты, проверить изображение, вычислить SHA и зарегистрировать отсутствующие метаданные под существующей блокировкой Storage. Физические пути и ссылки не меняются. Известные SHA не заменяются по догадке.
6. «Проверить устройство» и «Проверить облако (SHA-256)»: проверить результаты и скачать отчёты. Облачная проверка читает все приватные бинарные объекты, включая шрифты, и может расходовать трафик. Она проверяет существование объектов по ссылкам, наличие старых ссылок и незавершённых удалений. Не означает полноценную проверку каждого JSON или изображения на другом компьютере.
7. Повторить на каждом устройстве. Публичные публикации, оригинальные исторические JSON и незавершённые снимки синхронизации намеренно не перезаписываются. Старые публичные изображения защищены от удаления обычным Storage API: нельзя доказать отсутствие ссылок на отключённых устройствах и в экспортированных документах. Не удалять напрямую из storage.objects. Резервирования удаления не снимаются автоматически. Файлы вне учётного пространства не сканируются и не удаляются.

## Регрессия перед релизом
- `npm run build`; `node --experimental-strip-types --test tests/*.test.mjs`.
- Проверить два браузерных профиля с реальным Supabase, не только PGlite: создать локальный документ с PNG/JPEG/WebP, изменить размер, перетаскивание, отмена, повтор, быстрое сохранение; шаблон и фон мастер-слайда; перезапуск офлайн. Сохранение шаблона проверяется отдельно: прежний список таблиц транзакции не включал originalDocuments.
- Облачная загрузка: один SHA в двух методичках/шаблоне, одна приватная запись; убрать облачную копию, вернуть, проверить неизменное число объектов. Скачивание на B, офлайн-перезапуск. Временный просмотр не создаёт постоянной копии. Экспорт JSON импортируется в чистом офлайн-профиле.
- Старая локальная запись, старый шаблон, резервная копия, внешняя ссылка доступна/недоступна, оборванная сеть, повреждённый Blob с доступной и недоступной точной облачной копией. Повтор миграции не меняет уже корректные ревизии. Вход/выход, другой аккаунт и другая вкладка — не перезаписывают документ.
- Конфликты: сохранить локальную, облачную, обе версии; семь дней резервных копий и 30 дней корзины. Неиспользуемые изображения остаются; ручное удаление приватной копии и повторная загрузка; параллельные запись и удаление; потерянный ответ удаления; чужой UID/anon и прямые Storage API. Публичные старые объекты удалять запрещено.
- Опубликованная методичка открывается по ссылке без входа, приватные ресурсы не видны гостю. PDF/PPTX/JSON, папки, курсы, импорт, QR, редактор шаблона, просмотрщик работают как ранее. Галерея на узком и широком экране, скролл, ошибки доступа.
- Отчёты без необъяснённых ошибок. Пропуски не равнозначны успеху: разобраться в каждом. Не снимать защиту и не очищать данные ради прохождения теста.

## Откат
`--rollback` восстанавливает изменённые исходники, только если после патча их не меняли. Не откатывает SQL, IndexedDB и Storage. После миграции нельзя возвращать старый клиент, не понимающий компактные документы. Для отката данных нужна отдельная проверенная резервная копия/экспорт; не делать автоматический destructive rollback.
